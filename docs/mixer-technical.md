# Runtime, development and validation

## Project history

Fork baseline: `a76d44feaf01ad228aa99ed35531454be6fe1b4b` (Game Capture 0.2.62). The original project is independent and unchanged.

Previously named **Video Mixer**. Setup upgrades the existing installation and replaces its Start menu shortcuts. Existing shows, output profiles, camera settings, browser profiles and the layout preference carry over. The repository/build target, `%LOCALAPPDATA%/VideoMixer` data folder and `VDO.Ninja/Video Mixer` settings identity remain stable for compatibility. Older validation documents use the name of the version they measured.


## Engine and current limits

The original controls remain in **Capture & output**: standalone window/camera/Spout capture, hardware encoders, codecs, transparency workflows, audio encoding settings, and VDO.Ninja, WHIP, SRT caller/listener, RTMP/RTMPS, RTSP TCP/UDP, UDP MPEG-TS and RIST outputs. The **SRT mode** selector switches between connecting to a receiver and accepting a receiver at the configured local address. Passphrase encryption works in both modes. Listener output retries after stalled connections; it is not a permanent multi-client server. Rendezvous remains unsupported by this integration. Studio supplies frames and audio to that same output engine. Use the Studio faders when Mixer program is selected.

- The canvas supports native **720p30/60, 1080p30/60, portrait 720x1280/30/60 and 1080x1920/30/60**. Mixer streaming and independent recording follow that format. Stop outputs before changing it. Existing window/Spout sources reconnect to negotiate the new size and rate; webcams retain their separately selected capture mode. **Stacked** places interview pictures above one another; lock backgrounds/overlays before applying layout presets to preserve their placement. **CPU composition** is the default, based on lower measured cost for the common 720p mix. Optional **GPU composition** uses Direct2D/D3D11 with CPU fallback. Source/output frames still pass through CPU memory, so this is not a zero-copy GPU pipeline.
- New browser sources and the Advanced existing-chat path default to **Transparent overlay background**, using snapshots at up to **15 fps**. Overlay mode overrides the top-level HTML/body background to transparent on each navigation; message cards, embedded pages and other element styling remain intact. Social Stream Ninja can still supply its own custom CSS. Turn overlay mode off for opaque browser video using **Windows Graphics Capture targeting 30 fps**, avoiding PNG encoding/decoding. Existing saved capture modes are preserved. Actual cadence depends on hardware and page activity. The compositor still reads back to CPU memory.
- One streaming destination, plus independent recording, Spout output and virtual-camera output. **Spout output** publishes `Desktop Studio Program`. **Virtual camera** registers `Desktop Studio Virtual Camera` for the current Windows account without administrator access. It supplies video; select an audio device in the receiving app separately. This is a 64-bit DirectShow camera, verified in FFmpeg and Edge; applications requiring other camera interfaces may not support it. **Unregister camera** removes its registration. Local outputs start off each launch and are controllable through `local.set` in the CLI/API/MCP. Their producers run in separate workers, with bounded pending frames, crash/hang recovery and a restart limit. If an output pauses after repeated failures, turn it off and on to retry. Camera registration also runs outside the main app and UI thread.
- **Video / audio file** uses Windows Media Foundation codecs, including H.264/AAC MP4 and WAV. **Playback** offers pause, restart and looping. Local-file audio uses a 10 ms startup buffer and brief loop read-ahead to tolerate decoder jitter. Unsupported codecs report an error. Audio-only files contribute audio without occupying a video layout position.
- Cameras and native sources start asynchronously. Failed native captures retry with backoff; browser navigation failures and browser process crashes recover automatically. Windows restore by a unique executable/title match, including when their window reopens. Ambiguous or renamed windows require selecting the intended window through Reconnect. Missing devices/images/runtime report errors. Physical Logitech C920 unplug/reconnect recovered camera and microphone while recording and publishing continued; other camera drivers still need hardware coverage.
- Browser audio is routed from Web Audio/media streams to the native mixer. Browser speaker sessions are silenced; only enabled native monitoring plays locally. Ordinary Web Audio and WebRTC receivers are supported. Protected media, cross-origin media without CORS permission, and unusual page audio graphs may not expose audio; check the channel meter before going live. Chat overlays are visual sources.
- Application/desktop loopback audio needs Windows build 20348 or newer. Camera/mic capture and the browser audio bridge do not use that process-loopback API. Avoid capturing the same game's audio both individually and via Desktop audio.

## Browser runtime

Uses **Microsoft Edge WebView2 Evergreen**. No Chromium engine is bundled. Microsoft's runtime updates separately; users install it if missing. The SDK/loader is a build dependency, not the browser engine. [Microsoft distribution guidance](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution).

Profiles live under `%LOCALAPPDATA%/VideoMixer/browser/`. Receiving/overlay pages cannot access local cameras, microphones, screen capture or clipboard. Downloads, popups, external application handlers and non-HTTP(S) top-level navigations are blocked. The audio bridge validates the sending page, message size, type and rate; it exposes no native command or file API. Guests grant camera permissions in their own browser. Press Escape to park an interactive browser source.

Studio cameras, window/Spout inputs, microphones/desktop capture, media decoders, browser hosts, headphone playback, local Spout/virtual-camera producers, video encoders and each publishing/recording destination run in separate helper processes. Bounded frame/audio buffers prevent a slow consumer from building an unlimited backlog. A failed source reconnects; a failed publisher reconnects independently. A failed recording destination preserves its existing file and requires a new recording. Closing the app closes its helper process trees.

Still-image codecs also run in disposable helper processes, with at most two loads in progress, a 1 GiB memory limit per helper and a 15-second decode deadline. Loading a large or corrupt image leaves the interface and other sources running. PNG transparency is preserved; JPEG's runtime dependency is included in the portable package. Unsupported formats show a source error.

Each browser source and its Chromium children have a Windows CPU budget of at most half the machine, capped at four logical CPUs, plus a committed-memory limit of one quarter of physical RAM (minimum 1 GiB, maximum 4 GiB). All browser sources additionally share a CPU cap of half the machine or eight logical CPUs, whichever is lower, and a committed-memory cap of one third of RAM (minimum 2 GiB, maximum 8 GiB). CPU shares rebalance as sources enter/leave and retain shared headroom, so several busy pages cannot spend a healthy source's whole scheduling quota. Source health shows **CPU limit active** under sustained load. A page responsiveness watchdog supplements native worker heartbeats. After three automatic browser reconnects within a minute, a further failure pauses that source; **Reconnect** explicitly retries it. Complex pages and large guest panels may run more slowly when they reach a limit.

Browser audio routes into the source's mixer track by default. WebView2 retains its normal GPU rendering and compatible hardware video decoding, with software fallback for unsupported codecs/drivers. Transparent capture still uses CPU PNG snapshots at up to 15 fps; accelerated decoding does not make that capture path fully GPU-based.

On WebView2 152-154, a compatibility workaround avoids a WebRTC decoder reinitialization bug by not negotiating the RTP color-space extension. Enable **Preserve original video color metadata** in the source dialog if a source needs that metadata; this can cause software decoding on affected runtimes. Other runtime versions retain normal negotiation, and HTML video/HEVC support is unchanged. For VDO.Ninja, `&codec=h264` can request a codec with hardware decoding on compatible PCs; this was verified with a live feed. The source's codec selection is never changed automatically.

These boundaries contain user-mode failures in those components; they are not a guarantee against browser vulnerabilities, an OS/GPU-driver failure, or bugs in the main compositor. Compositing, image-buffer handling and some inherited non-Studio paths still include native code in the main process. Keep Windows, graphics drivers and Evergreen WebView2 updated.

## Build

Requires Windows x64, Visual Studio 2022 C++ tools/Windows SDK, CMake 3.24+, Ninja, and Qt 6 Widgets/Network/Concurrent. The script uses `VCPKG_ROOT`, or `C:/vcpkg` when unset.

Portable/installer packaging also requires `qtimageformats[core,webp]:x64-windows` from the same vcpkg installation as Qt. Install it with `vcpkg install "qtimageformats[core,webp]:x64-windows"`. The package includes the WebP plugin, its runtime libraries and notices so profile photos work without development tools on the destination PC.

```powershell
# Prepare FFmpeg for recording, RTMP/SRT and FFmpeg-dependent codecs:
powershell -ExecutionPolicy Bypass -File native-qt/tools/fetch-ffmpeg-lgpl.ps1

# Restore the WebView2 SDK, configure, build, and package Qt:
powershell -ExecutionPolicy Bypass -File native-qt/build-mixer.ps1 -Package

# Also build the per-user setup executable (requires NSIS 3):
powershell -ExecutionPolicy Bypass -File native-qt/build-mixer.ps1 -Installer
```

Portable executable: `native-qt/dist/desktop-studio-portable/desktop-studio.exe`.

Archives and setup: `native-qt/dist/desktop-studio-0.9.1-windows-x64.zip` and `desktop-studio-0.9.1-setup.exe`. Setup installs under `%LOCALAPPDATA%/Programs/Desktop Studio`, includes Qt/VC runtime DLLs, creates Start menu shortcuts, and preserves shows/recordings on uninstall. It does not bundle WebView2 or modify firewall rules. Release notes identify package signing and validation status. `installer-mixer.nsi` is the current installer; `installer.nsi` remains the inherited machine-wide installer.

The pinned SDK is fetched from NuGet; other native dependencies use CMake FetchContent. Downloaded dependencies, build outputs, local shows, and QA artifacts are excluded from Git.

## Built-in chat (milestone 1)

`ChatEngine` runs `ProcessWorker("chat")` on a dedicated thread, using inherited handles and a kill-on-close Windows job. The entire chat tree, including WebView2 descendants, participates in the existing aggregate browser budget. Its hard private commit limit is 1,024 MiB; the supervisor restarts chat at 960 MiB or a job memory-limit event. CPU is hard-capped at the smaller of two logical cores and 25% of machine capacity, further reduced by fair sharing of the aggregate budget. Fifteen seconds at >=90% of its current CPU allowance triggers recovery. Sampling is once per second. The existing browser-source limits remain intact. Last approved comment pixels, mixer, recording and streaming workers are independent of this recovery.

`chat.status.resources` reports `private_mib` (sum of accessible job processes' PrivateUsage), `peak_job_mib`, `memory_limit_mib`, `cpu_cores`, `cpu_percent` (100% = all logical processors), `cpu_limit_cores`, `processes`, `measured_processes`, and `limit_exceeded`. CPU uses Windows job accounting deltas; memory samples can omit a process that exits during enumeration. Resource recovery has a plain-language status for ten seconds. Validate budgets with live pages and overload runs before treating them as qualified production limits.

A lifetime `chat-owner.lock` protects both app-level `chat.json` and ownership of the shared WebView2 profile. A second Studio instance fails closed before loading channels or starting chat. The worker separately locks `chat/studio-profile.lock`; this handles overlap during worker shutdown/restart. Settings are written atomically with `QSaveFile`, and unreadable settings remain untouched. QLockFile does not steal a lock just because a live owner is old.

Chat starts only with channels or practice. The three engine-side pages (background, host transport and featured output) all have active roles; no extra engine page is created. The featured page is already eager-loaded, and readiness now includes its bridge peer. One environment has separate `capture` and `engine` profiles. Capture HWNDs/controllers remain hidden; only featured renders. Capture requests block images, media, fonts and selected advertising/tracking domains, retaining DOM URL attributes, scripts, chat sockets and data requests. Each capture document receives only matching manifest script groups, including the corresponding all_frames scripts. The inspected pack contains 4,300,410 script bytes across all entries, versus 97,763 for Twitch and 127,634 for YouTube. These are source sizes, not measured process-memory savings.

The native capture boundary uses WebView2's actual message Source and frame event sender. Capture frames post directly through their own native WebMessageReceived API, never via an unrestricted top.postMessage relay. A child must match an all_frames entry associated with the enclosing capture page, including match exclusions/globs. Frame replies use that frame's native interface. Nonmatching frame navigations are cancelled; inert about:blank is allowed but cannot send capture RPCs. Top-level redirects remain on the channel's platform and allowed capture/resolver routes. Cross-origin frames explicitly listed in the same manifest entry, such as eBay's shoplive frame, remain eligible. This is main-world capture, not an isolated Chrome extension world; the platform's own page can still manufacture its own messages. Nested-frame runtime compatibility still requires external platform testing.

Capture pages may send bounded comments or request settings. Native code assigns channel/tab/platform and denies other capture RPCs. Local bridge membership is restricted to engine/host/overlay pages. The socialstream.ninja virtual host maps only to the verified local pack; VDO bridge documents are intercepted locally and cloud relay/signalling is blocked. Host objects, downloads, permissions, popups and native input/page-creation APIs remain disabled. Payloads do not enter normal logs. SSN processes captures; the host converts HTML-mode bodies to literal text in an inert DOM parser. Qt paints strings, and featured receives textonly bodies with escaped author names.

Before reading/executing pack code, both Studio and the chat worker verify SHA256SUMS, the manifest digest in pack-version.json, all referenced bytes, containment and absence of extra files/symlinks. Failure makes chat unavailable. This detects damage or stale installed assets; it is not a digital signature against replacement of the entire package and its digest files. The installer removes its entire installed ssn directory before copying the new pack. `sync-ssn-pack.ps1` reads SSN_ROOT (default sibling social_stream) without modifying upstream, and builds the static dependency closure with licence/digest metadata. No upstream files or engine source bytes are patched.

YouTube `/live` resolution keeps retry deadlines outside document navigation: 60, 120, 240, then 300 seconds while offline. After attaching, periodic probes continue; a lightweight same-origin watch-HTML request (once per minute, no player/subresource load) supplies channel identity and broadcast status. Ended/offline/unavailable broadcasts resume the channel resolver. Native HTTP 404 and platform-owned error panels/structured state distinguish missing channels, sign-in, offline streams and unavailable chat. Status detection never scans viewer comments. Instagram/TikTok have explicit visible sign-in and limited known offline/error probes; this is not exhaustive localization support.

The native model caps both displayed and pending comments at 2,000. Insert/evict signals are batched; releasing a full paused list no longer emits 2,000 individual insertions. SelectionItem-only accessibility events and current-index changes use the same handler. Missing/empty chat.select IDs deselect and flush buffered rows. The painted delegate uses compact avatar/name/platform/donation rows with saved/on-air tags; no per-row widgets are allocated.

Comments remain a show-level layer above scene transitions. Its enabled/style/normalized rectangle persist in the show; channels persist outside it. Private break covers the layer and pauses its timer. A new Show is acknowledged only after the bridge token, literal text, output opacity and PNG snapshot agree, then Program actually composes it. Recovery retains the last approved pixels until Hide or the existing timer expires, without resending comments.

Featured's default code waits 500 ms before its render callback and normally animates for another 500 ms. Studio supplies transition=none and CSS disabling transitions. Its shim schedules the real 500-ms callback immediately only for explicitly studioToken-tagged cards, preserving the callback and arguments. Render readiness polls every 33 ms, the token observer every 16 ms, and Studio drains the worker result every 33 ms. Periodic transparent PNG snapshots retain 67-ms cadence; first Show captures immediately once ready. `chat.status.timing` separates startup (overlay load/bridge, engine ready), worker dispatch/render/snapshot/PNG decode/shared-memory transfer, Studio frame receipt and composition. The <500-ms target is not yet measured on the revised build.

The dock is 372 logical pixels at normal widths, collapses below 1,240 window pixels, and uses theme colours with fixed contrasting blue/amber state accents. First-run setup has a nearby practice action; connected channels move that action under Advanced. Three Bar/Bubble/Big buttons replace the combo box. The private Qt preview and amber live-countdown band are separate. On-screen cards still use SSN's noavatar option; initial avatars are in the native list. Position remains an Advanced dialog, saved bookmarks last for the run, and later-milestone replies/sign-in/viewer tools remain absent. Spanish/French include the new states. Kick uses /popout/<channel>/chat, also used by SSApp and the upstream capture script. Rumble uses its channel /live or /chat/popup/<id> routes; its API/WebSocket connector is not substituted.

Use VIDEO_MIXER_DATA_DIR for an absolute writable test folder. It isolates chat/settings/logs/shows/profiles. All Studio preference constructors explicitly take QSettings::defaultFormat() and UserScope, so the configured INI paths apply; the two-string constructor ignores setDefaultFormat (see [Qt documentation](https://doc.qt.io/qt-6/qsettings.html#setDefaultFormat)). With no override, NativeFormat remains the default. Never use the real VideoMixer folder for development runs. All four existing drivers retain their commands; VIDEO_MIXER_CHAT_EXE optionally selects another packaged artifact. The packaged workflow adds a real-engine 500-comment burst scheduled at 50/s, empty selection/input checks and stage timings; the live driver records job resources/timings, the platform probe records resolved names/resources, and UI Automation covers deselection/countdown at 1280 px. `chat-offline-workflow.mjs` exercises actual packaged input/ownership/setup workflows without needing browser readiness. `run-chat-gates.ps1` runs deterministic gates, not end-to-end testing. Current evidence and remaining work are in mixer-chat-m1-validation.md.
